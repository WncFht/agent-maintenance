# 检查、调度与接线

优先使用目标现有工具。维护包提供 Notes 格式与冻结检查、本地文件链接与技能结构检查、暂存快照验证及小型调度器；hooks 与 CI 复用这些检查，执行关系见[维护流程](../../docs/pipeline.md)。本地锚点与篇幅检查见[检查边界](document-budgets.md)；不声称覆盖产品行为、外部链接或包依赖。

| 验证面              | 建议采用的真实证据                             |
| ------------------- | ---------------------------------------------- |
| 源码行为            | 所属测试、必要的真实组合与外部可观察结果       |
| 类型与脚本          | 对应类型检查；确认测试与脚本是否属于被检查项目 |
| 文档                | 现有 Markdown、链接、示例编译和命令运行检查    |
| 生成物              | 来源生成器的确定性 --check                     |
| CLI、模型或用户输出 | 实际入口场景和所属快照                         |
| 包、入口与构建      | 真实构建、打包安装、受支持消费者 smoke         |
| 持久化与网络        | 类型或格式变更声明、前后代真实读写及兼容测试   |
| 性能                | 基线、原始样本、端到端与内存、反向验证         |
| 决策归档            | 当前哈希及可信历史基线比较                     |

本地 hook 做便宜而明确的暂存检查。按 diff 的本地验证覆盖实际变更；CI 承担全量和平台矩阵。不要把依赖配置自动补齐、发布或合并混入只读检查。

scripts/checks.json 的命令必须是参数数组，不经过 shell。needs 依赖成功才运行；失败导致后代 skipped，阻断项的 skipped 也是失败。allow_failure 保留观察信号但不把该项当通过，不能满足需要它成功的后代。mode 只选择一组检查及其依赖，不证明选取覆盖全部变更。

notes_guard --base 的基线必须由可信工作流确定。CI 获取目标历史，验证 base 属于可信目标，再传入完整提交；不得把用户可改的 manifest 当唯一权威。源码策略也不能从待审 PR 加载执行后宣称能抵御恶意修改；需要攻击防护时，校验器本体同样来自可信版本。该工具主要防止常规误改，不是 OS 沙箱。

新检查器必须证明：有效数据通过、违规非零、空集合和忽略边界符合预期。静态检查不能正确解释动态消费者时，缩小承诺或撤掉工具，而不是永久堆例外。

run_checks 仅限制直接子进程的运行时间，不提供跨平台进程树监督。会生成后台进程的检查应由所属测试框架保证取消、退出与清理；不要把本调度器当作生命周期隔离层。输出尾部限制为 16000 字节，完整输出暂存在临时文件中，因此大输出仍会消耗磁盘。

只有远端 required checks/ruleset 实际启用才会阻止合并。配置文件存在、当前命令通过和远端合并保护生效是三个不同事实。
